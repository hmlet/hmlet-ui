# Migration Notes — v2.0.0

## What changed

Dark-mode primary buttons now render in the brand orange (`#FF7960`) instead of
the previous near-white/gray fill. This comes from a new dedicated button token
family that the `Button` component's `default`/`primary` variant now consumes
instead of the generic `primary` tokens:

| New CSS variable                               | Light     | Dark      |
| ---------------------------------------------- | --------- | --------- |
| `--btn-primary`                                | `#251f42` | `#ff7960` |
| `--btn-primary-hover` (also used for `active`) | `#352d5c` | `#ffb2a3` |
| `--btn-primary-foreground`                     | `#ffffff` | `#241e3b` |

All other button variants (`primary-outline`, `primary-ghost`, `link`) and other
components that read `--primary`/`--primary-dark` directly are **unchanged** —
only the solid CTA fill moved to the new tokens.

Also added: a `tile-*` token family (`tile-fire`, `tile-medical`, `tile-power`,
`tile-neutral`, each with an `-ink` text variant, light + dark) for
category-coded UI such as the Emergency Contacts cards in the new Member Portal
designs. No shipped component consumes these yet — they're available for
upcoming work.

The `ThemeColors` type (exported from `theme/ThemeProvider`) grew 11 new
required keys: `btn-primary`, `btn-primary-hover`, `btn-primary-foreground`,
`tile-fire`, `tile-fire-ink`, `tile-medical`, `tile-medical-ink`, `tile-power`,
`tile-power-ink`, `tile-neutral`, `tile-neutral-ink`.

## Why

Design refreshed the Figma color spec ("hmster Semantic" collection) for the
Member Portal redesign. It decouples the navy "brand surface" color (stays dark
in dark mode) from the "primary CTA" color (goes orange in dark mode for
sufficient contrast/visibility against dark backgrounds) — previously both were
driven by the same `--primary` token, which meant dark-mode primary buttons
rendered near-white instead of the intended orange.

## Who is affected

- [x] Tenant app
- [x] My page
- [x] Hmster
- [ ] Other: \_\_\_\_

Anyone rendering `<Button variant="primary">` or `<Button variant="default">`
(the default) will see the dark-mode fill color change with no code change
required on their end — this is a visual-only break, not an API break.

**Only if you pass custom `lightColors`/`darkColors` to `ThemeProvider`:** your
color map must now include the 11 new keys above. TypeScript will fail to
compile a `ThemeColors`-typed object missing them; if the type check is bypassed
(e.g. a cast), the missing keys resolve to `undefined` at runtime and
`ThemeProvider` will set the corresponding CSS variables to the literal string
`"undefined"`, breaking the new button fill and any component that later adopts
the `tile-*` tokens. Consumers using the library's `defaultLightThemeColors`/
`defaultDarkThemeColors` unmodified are not affected.

## Upgrade steps

1. Upgrade the `@hmlet/ui` pin and reinstall.
2. Visually check dark mode: primary buttons (default/primary variant) should
   now be orange. If your app has snapshot tests or visual regression tests
   covering primary buttons in dark mode, expect them to need re-baselining.
3. If you pass custom `lightColors`/`darkColors` to `ThemeProvider`, add the 11
   new keys (see table above for the default light/dark values, or use them as a
   starting point for your own brand values).
4. No action needed for `tile-*` tokens unless you're adopting the upcoming
   category-tile component pattern.

## Codemods / automated helpers

None — manual update only. The button color change requires no consumer code
changes; the `ThemeColors` key addition is a values-only fill-in, not a
mechanical rename.

## New peer dependency requirements

None.
